# Identity (step 10): certificates, wire v2, revocation, scope

Status: in code, 2026-11-04, slices 1 to 4 (`COMPLETED.md`).

Written 2026-11-04 from the plan ("Identity and scope") and Tom's answers
the same day (Decisions, 2026-11-04): X.509 through OpenSSL; certificates as
wire version 2 beside version 1; the CA key offline, used through a
`dannan-ca` tool. Lugh's requirements (a node revoked at once; a node's key
held like Lugh's master key) and the scope seam (Decisions, 2026-11-04) are
part of it.

## 1. Certificates

- **The cluster CA**: an EC P-256 key and a self-signed X.509 certificate,
  basicConstraints CA:TRUE with pathlen 0, keyUsage keyCertSign and
  cRLSign, a subject naming the cluster. Its key is sealed like node
  custody (systemd credential or Argon2id passphrase) on an operator's
  machine, never on a node.
- **A node certificate**: issued by the CA over the node's own public key
  (the ES256 key in its custody), basicConstraints CA:FALSE, keyUsage
  digitalSignature, a subjectAltName URI `dannan:node:<32 hex digits>`
  naming the node id, a serial, and a validity of two years by default.
  The node id is the certificate's, never the address (the plan).
- **The cluster id** is the first 16 bytes of SHA-256 over the CA
  certificate's SubjectPublicKeyInfo: every node of one CA is one cluster.

## 2. Wire version 2

**In code (2026-11-04, slice 2).** As built: the hello's body (as v1's,
without the cluster id) is followed by a count of proofs, each a kind (1:
cluster key, 2: certificate), the cluster it proves, then the HMAC (v1) or
the certificate DER and signature (v2). The ack carries the proof of the
version chosen.

The hello and ack keep wire v1's layout up to the record, then carry an
authentication block chosen by version:

- **v1**: as today, an HMAC under the cluster key's auth key.
- **v2**: the sender's certificate (DER) and an ES256 signature by its node
  key over a label (`dannan/hello/2`, `dannan/ack/2`) and the transcript so
  far (the ack's over hello and ack, as v1's MAC is).

A hello states the versions it speaks and carries the block for each it
can prove (a node with both a cluster key and a certificate carries both);
the server picks the highest version both speak and checks that block. A
v2 check: the certificate chains to this cluster's CA, is in its validity
at the receiver's wall clock, names the hello's node id, is not revoked,
and the signature verifies under its key. Session keys are derived as in
v1, salted with the cluster id instead of the auth key, bound to the
transcript and both certificates' hashes. Purpose and path token are
unchanged.

## 3. Revocation

A **revocation** is a record the CA signs (ES256 over its encoding): the
node id, the certificate serial (zero: every certificate of that node),
when, and why. Revocations are grow-only: gossiped as a set beside identity
resets (a core message type), persisted under the state path
(`DNNREV01`), and checked at every v2 handshake. A node that learns one
closes its sessions with that node at once, so a revocation takes effect
immediately on the node it is given to and cluster-wide within one gossip
round. A revocation's signature is checked against the CA before it is
kept or passed on.

## 4. The tool

`dannan-ca`:

- `init`: makes the CA key (sealed) and certificate.
- `issue`: a node certificate for a node id and public key (printed by
  `dannan-node --show-key`).
- `revoke`: a signed revocation, to hand to any node.
- `show`: what a certificate or revocation says.

## 5. The node

`NodeConfig` gains the CA certificate, the node's certificate, and its key
custody (already there). A node with a certificate speaks v2; with a
cluster key, v1; with both, both. The Context's `Identity` gains the node's
certificate and `revoke(revocation)` (applied and propagated).

## 6. Scope

`contract::ScopeSource` (declared by Dannan, installed by Lugh): may
principal P write under prefix S, read from memory, with the generation it
read as evidence. `Identity::verify(principal, prefix)` checks through it;
with no source installed, the node's own principal and any certified
cluster node may write, nobody else.
